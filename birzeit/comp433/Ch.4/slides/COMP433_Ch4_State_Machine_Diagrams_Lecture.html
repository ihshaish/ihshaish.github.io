Where we are: from behaviour to lifecycle

Four diagrams, four questions about one system. The class diagram says what exists; the sequence diagram, one interaction between objects; the activity diagram, how one task flows. The state machine is the last cut: one object, its entire life, every state it can be in and every event that moves it.

The cut
Sequence is a horizontal slice (one scenario, many objects). A state machine is the vertical slice: one object, many scenarios, over its whole lifetime. Draw it for an object whose behaviour depends on its current state.

What a state machine is, and when to draw it

A state machine models the states an object passes through in its lifetime and the events that cause transitions between them. Read it by following events from the initial state.

What it captures

  • The finite set of states the object can be in.
  • The events that trigger transitions, with guards.
  • The actions and activities each state and transition runs.
  • Which operations are legal in which state.

What it does not capture

  • Interactions between several objects (sequence).
  • Static structure (class diagram).
  • A business workflow across actors (activity).
When
Draw one when an object's behaviour depends on its state (the same call does different things, or is illegal, depending on state) or it has a real, observable lifecycle: a Loan, Order, Ticket, Account. Skip it for passive data carriers and value objects.

Where the states and events come from

A state machine is anchored to the class diagram: it describes the lifecycle of one class's instances.

In the state machineComes from
The object whose life is drawnone class from the class diagram
Statesthe meaningful conditions of that object (often the values of a status attribute)
Events (call events)the operations declared on the class
Guardsbusiness rules and multiplicities from the requirements
Consistency
Every call event should match an operation on the class, and the states should explain why an operation behaves differently at different times. If a state needs an event the class cannot raise, the class model is incomplete.

Theory: finite automata, and Moore vs Mealy

A state machine is a finite-state automaton: a finite set of states, an alphabet of events, and a transition function mapping a (state, event) pair to a next state. It is the oldest rigorously understood model of behaviour in computing, which is why it drives compilers, protocols and controllers.

Moore machine

Output depends only on the state. In UML, the entry / do / exit activities are Moore-style: they run because of where you are.

Mealy machine

Output depends on the transition (state and event). In UML, the / action on a transition is Mealy-style: it runs because of what happened.

UML deliberately allows both. Knowing which you mean, a state's entry action or a transition's action, keeps the diagram unambiguous.

Theory: run-to-completion, and determinism

Run-to-completion

UML processes one event completely before starting the next: a transition, with its guard check and action, runs atomically, and events arriving meanwhile queue. This is what makes a machine implementable and free of mid-transition races, and why guards must be side-effect-free and actions short.

Determinism

From any state, an event and its guards should select at most one transition. Two transitions on the same event with overlapping guards is nondeterminism, a modelling error, and exactly the defect the diagram exists to expose.

State explosion
A flat machine modelling n independent on/off features needs 2n states. Harel's statecharts (1987), which UML adopts, tame this with hierarchy, orthogonality and history, covered shortly.

Notation: states, transitions, activities

A state is a rounded rectangle (optionally with an activities compartment). The initial pseudostate is a filled dot; the final state a bullseye. A transition is an arrow labelled event [guard] / action, any part optional. A self-transition handles an event without leaving the state.

Events, guards, actions, activities

PartMeaning
EventThe trigger. Call (an operation, borrow()); signal (an async message); change, when(balance < 0); time, after(30 days) / at(09:00). No event = a completion transition (fires when the state's activity finishes).
GuardA side-effect-free boolean in [brackets]; across one state's transitions on the same event, guards should be mutually exclusive.
ActionInstantaneous, uninterruptible: on a transition (Mealy), or on entry / exit of a state (every time it is entered or left).
Do-activityOngoing work while in a state (do / countDays()), interrupted if an event causes an exit.
Internal vs selfAn internal transition does not re-run entry/exit; a self-transition exits and re-enters, so it does. Confusing them is a real bug.

The smallest meaningful machine: a turnstile

Two states, two events. It is the canonical teaching FSM because it shows the whole idea with nothing to spare: the same event does different things depending on the state.

A coin in Locked unlocks; a push in Unlocked locks. The self-transitions capture the awkward cases the requirements must answer: a push while Locked (alarm), a second coin while Unlocked (no extra effect). A state machine forces you to decide what every event does in every state.

Taming complexity: composite, orthogonal, history

Harel's three extensions, which UML adopts, keep a real diagram readable.

Composite & orthogonal

A composite state nests a sub-machine; a transition out of it (cancel) applies to all sub-states at once. Orthogonal regions, split by a dashed line, are active simultaneously, so independent concerns add rather than multiply.

History

The circled H remembers which sub-state was active when the composite was last left, so re-entry resumes there. It is how a "resume where you left off" feature is modelled.

Worked example: the BookCopy lifecycle

  1. A copy starts Available (its entry / shelve() runs as it is put on the shelf).
  2. borrow() moves it to OnLoan, whose do / countDays() runs while the loan is live; return() brings it back to Available.
  3. The time event after(3 weeks) [overdue] moves an unreturned copy to Overdue (entry / notifyMember()); returning it still goes back to Available.
  4. From either active state, reportedLost moves the copy to the terminal Lost state, charging a fee, and the lifecycle ends.

How to build one

Recipe

  1. Pick the class whose lifecycle matters.
  2. List its distinct states (conditions in which it behaves differently).
  3. Draw one initial pseudostate and the final state(s).
  4. For each state, ask which events are legal and where each leads; label transitions event [guard] / action.
  5. Add entry/exit/do where behaviour belongs to the state itself.
  6. Nest related states into a composite when the picture grows.

Sanity checks

  • Every state is reachable, and the machine can reach a final state (no dead ends, unless intended).
  • For each state, every legal event is handled (decide the awkward ones).
  • Guards on one event are mutually exclusive (determinism).
  • Every call event matches an operation on the class.

Pitfalls

  • A state machine for a passive object. If there is no state-dependent behaviour, you are drawing a class's data, not its life.
  • States that are really data. "HasThreeBooks" is an attribute value, not a state; a state changes behaviour.
  • Unhandled events. Leaving a (state, event) pair undecided is the commonest defect; decide it, even if the decision is "ignore" or "alarm".
  • Nondeterminism. Two transitions on the same event with overlapping guards.
  • Actions with side effects in guards. Guards must only test, never change.
  • State explosion. A flat diagram with dozens of states; use composite and orthogonal states.

Where state machines earn their place

Where they dominate

  • Embedded and safety-critical control (Stateflow, DO-178C / ISO 26262).
  • Network protocols (TCP's 11-state machine, RFC 793).
  • UI state management (statecharts, XState).
  • Domain object lifecycles (orders, loans, tickets).

What they do not solve

  • Multi-object interaction (sequence).
  • Static structure (class).
  • Cross-actor workflow (activity).

Tooling: MATLAB Stateflow for safety-critical work; XState and SCXML for software; PlantUML and Mermaid for documentation; AWS Step Functions as an executable cloud state machine.

Recap, and the four views together

Hold on to

  • A state machine is one object's whole life: states, events, transitions.
  • Transition label: event [guard] / action; entry/do/exit live in the state.
  • Run-to-completion and determinism keep it implementable.
  • Composite, orthogonal and history tame complexity.

The four behavioural/structural views

Use case (who and what), class (what exists), sequence (one interaction over time), activity (one task's flow), and state machine (one object's life). Each answers a different question about the same system; together they are the working core of UML for analysis and design.
